Part Lifecycle Tracker

A full-stack manufacturing app that tracks an assembly line part across its entire lifecycle — from a customer order, through supplier purchasing and physical receipt, through assembly with enforced build order and dual sign-off, to a certified finished unit. The central bet: separate what a part is supposed to be from what physically exists, and record every change as an immutable event, stamped with who did it.

The problem

Most tools conflate the design with the object

Manufacturing software routinely treats "a part" as one thing. But the design of a part and the physical objects built from it have different identities, different lifecycles, and different questions asked of them. Once that distinction is lost, you can't answer the question that matters on a shop floor: "Did serial HMR-0047 get the Rev C dome or the Rev B one — and who validated it?" Those answers end up living in spreadsheets and people's heads. This project encodes them in the system instead.

The core design bet

Two entities, not one

Every other decision in the system follows from this split.

Part Definition

e.g. THE-HOMER-001

The design artifact. One per part number. Carries a bill of materials and a DRAFT → RELEASED → OBSOLETE lifecycle. Once released, the revision and BOM lock.

  • Answers: what is this part supposed to be?
  • BOM with multi-prerequisite dependencies
  • One identity per part number
VS

Part Instance

e.g. HMR-0047

A physical object with a serial number — one of many built to the same part number. Its entire history is an append-only event log — never updated, never deleted.

  • Answers: what physically exists, and where has it been?
  • Status derived from the latest event
  • Dual timestamps: when it happened vs. when it was recorded

Key design decisions

The calls that make it interesting

Each of these was a deliberate trade-off — the kind worth defending in a design review.

data model

Append-only event log

Every state change is an immutable event with dual occurred_at / recorded_at timestamps. You get audit trails and "where has this been" for free — current status is just the latest event, denormalized for fast queries.

business rule

Hard dependency enforcement

Try to assemble a step before its prerequisite and the API returns 409 DEPENDENCY_NOT_MET, naming the blocker — not a warning. Safety-critical build order belongs in the system, not in tribal knowledge. (The canonical test: muzzle-before-dome.)

workflow

4-eyes assembly

Install, validate, and certify are three separate endpoints, each stamped with the authenticated actor from the session. The validator can't be the installer (409 SAME_ACTOR); only QA certifies. "Was it installed," "was it installed correctly," and "does it work" are different questions asked by different people.

API design

A /context endpoint for AI agents

One endpoint returns a rich, self-contained snapshot of a part — designed to drop straight into an LLM prompt. The summary string is templated from data, not LLM-generated, so it's deterministic, fast, and safe.

architecture

Rails API + React, not Hotwire

The default Rails answer is Hotwire — server-rendered HTML, one codebase, fastest path for a solo build. Splitting into an API-only backend and a React SPA was deliberate: the API is the product here. The SPA consumes the same documented endpoints as any other client — no private routes propping up the UI.

authentication

Real passwordless login

Authentication is real Stytch passwordless — magic links, plus one-click demo personas that mint real sessions. Every event records the authenticated actor; there's no "who are you" field to fill in.

authorization

Roles the client can't pick

Each identity gets its role server-side (RBAC). Actions you're not permitted stay visible but disabled — with the reason — and the server enforces them anyway (403 FORBIDDEN). An email that isn't a seeded user gets a read-only session.

data integrity

Invariants live in the database

Model validations are convenient; constraints are law. Status enums, positive quantities, non-negative stock, and even the four-eyes rule (validated_actor <> installed_actor) are Postgres CHECK constraints — a buggy code path or a console session can't write an invalid row.

tooling

Code-first OpenAPI

The API spec is generated from real RSpec request specs (via rspec-openapi), not a hand-written parallel DSL. A doc derived from real test traffic is accurate by construction — which matters when an AI agent is a first-class consumer.

testing

The database is never mocked

Every spec runs against real PostgreSQL — the invariants live there, so mocking it would test a fiction. A per-PR coverage gate (undercover) fails CI when new or changed code isn't exercised by a test.

data model

Event-sourced instances, counter-based stock

Event sourcing earns its complexity for identity-bearing objects. Fungible inventory doesn't have identity, so stock is a plain counter plus an audit log — simpler, and sufficient. Use the right tool per entity.

scope

A ruthless v0

Built as a minimum viable product, which meant deciding what not to build: no revision-approval workflow, no cost rollup, no multi-tenancy, no where-used queries. Every cut is written down — scope discipline is a design decision too.

Built for humans and agents

The secondary consumer of this API is an AI agent. GET /parts/:id/context exists so an agent can answer questions about a part from a single response — validated by a dogfood test: paste the response into Claude, ask four questions, all must be answerable. The whole API is documented from real traffic, so the contract an agent reads is the contract the server honors.
